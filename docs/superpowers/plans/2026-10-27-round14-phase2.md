# Round 14 Phase 2 (C: purchasing with simulated OCR) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Anyone who buys can photograph a nota or a Tokopedia order. A simulated OCR fills in the item lines, finance reviews the itemised receipt, and finance and management see where the money goes on a new Spending screen.

**Architecture:**
- **Shared code:**
  - The purchasing data (types, the simulated catalogue, line rules, spending maths) lives in `packages/shared` and is pure and unit-tested.
  - The existing `receipt.add` and `receipt.edit` actions and the directory actions gain fields.
- **Server:** one new endpoint, `POST /api/receipts/read`, calls a swappable `ReceiptOcr` provider. The simulated provider wraps the shared catalogue.
- **Web:**
  - One capture component (photo → reading → lines → section → send) replaces both current snap panels: Receipts for finance and management, Requests for section staff.
  - A new Spending screen reads the synced state.

**Tech Stack:** TypeScript, pnpm monorepo, immer actions, Hono, React 18, vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-23-round14-ops-team-design.md` §Phase 2 — C (C1–C4), plus its Conventions and Testing sections.

## Global Constraints

- Shared immer actions live in `packages/shared/src/actions`, pure rules in `packages/shared/src/rules`, and role checks are server-side through each action's `can`.
- The UI is dense and phone-first: 44 px touch targets, ink, grey and white with the warm staff skin, no pastel tints, filters as dropdowns.
- Every new string exists in EN and ID. The ID file is typed `Same<typeof EN>`. Add a new namespace `purchasing` (`i18n/en/purchasing.ts`, `i18n/id/purchasing.ts`), registered in both `index.ts` files the way `renewals` is.
- Every integration stays simulated, but behind a provider interface: "A real provider (a vision model or a document-AI service) replaces the simulated one by config; nothing in the screens changes."
- `amount` stays the receipt total.
- **Seed:**
  - It stays RNG-neutral: new draws use keyed `unit('<key>')` from `seed/history.ts` and never the shared stream.
  - `CP_SEED_SMALL=1` keeps working.
  - The club state stays under the 7,500,000-character cap at the real date and at 2026-12-30 (`seed/history.test.ts`).
- **Tests:** typecheck, unit tests for new rules and actions, and one e2e pass of the phase story on a phone viewport (`scripts/e2e-all.sh` pins CP_DEMO_DATE=2026-10-21, CP_SEED_SMALL=1).
- **Ports:** dev API 8788, web 5173.

## Rulings made while writing this plan (KC to confirm in review)

- **R1 Categories:** a fixed list of eight, translated, not a table finance can extend. "The list is editable by finance in the Directory" is read as: finance sets each supplier's category in the Directory form. *Cost if wrong:* a `spendCategories` collection with add/rename later.
- **R2 Old receipts:** `Receipt.source`, `orderNo` and `lines` are optional in the type, so receipts already in Postgres stay valid. Readers use `r.source ?? 'shop'` and `r.lines ?? []`. In Spending, a receipt without lines counts its whole total under its supplier's category (or Other).
- **R3 Line categories:**
  - An OCR line keeps the catalogue item's own category.
  - A line added by hand takes the supplier's category, unless the supplier is an Online marketplace.
  - Otherwise the line's category is Other.
  - Reason: every Tokopedia line would otherwise land under "Online marketplace", which says nothing about what was bought.
- **R4 Totals that don't match:** a mismatch between the lines and the total is a warning, never a block. Tokopedia totals include shipping, and shops round.
- **R5 One capture flow for every buyer:** the Requests "Snap a receipt" panel (nurse, activity, kitchen, lobby) uses the same capture component as Receipts. The fake camera there becomes the real `CameraCapture` with an upload, because the OCR needs a `mediaId`.
- **R6 Where the lines show:** finance sees the lines by expanding "N items" on the receipt row (there is no receipt sheet today). Edit can change the lines.
- **R7 Item price trend:** the item row shows the change from the first to the last unit price in the period (▲/▼ %). The item's sheet shows the price as a `TrendChart` over every purchase.
- **R8 Spending periods:** This month, 3 months and 6 months are calendar months ending today (3 months = the 1st of the month two months back to today). Custom is From and To dates.

## Review Focus

1. **The OCR fails** (network error, unknown photo, or a server error): the form stays usable by hand. An inline "Couldn't read the receipt. Fill it in by hand." shows and the lines start empty. *Test: Task 3.*
2. **Retake after the lines were filled:** the new photo is read again and its lines replace the old ones. *Test: Task 3.*
3. **A bad line** (blank name, quantity 0, negative price): Send stays disabled with that line marked, and the server refuses the same input. *Tests: Task 1 (action) and Task 3 (UI).*
4. **Taps while reading:** Send and the fields are disabled during "Reading the receipt…", and a second photo cancels the first read (the last photo wins). *Test: Task 3.*
5. **What Spending counts:** only approved receipts that aren't voided and fall in the period. A period with none shows the empty state. The same item name with different units stays as two rows. *Tests: Task 5.*

**Interfaces:**
- Consumes: `OcrResult` and `simulatedReceipt` from Task 1; `loadMedia(id)` from `media.ts`; `authUser(c)`.
- Produces:
  - `export interface ReceiptOcr { extract(input: { mediaId: string; mime: string; bytes: Buffer; today: ISODate }): Promise<OcrResult> }`
  - `export function receiptOcr(): ReceiptOcr`: chosen by `process.env.CP_OCR_PROVIDER` (only `'sim'` exists, and it is the default; an unknown value throws at boot).
  - `simulatedOcr`: waits `Number(process.env.CP_OCR_DELAY_MS ?? 1500)` ms, then returns `simulatedReceipt(mediaId, today)`.
  - Route `POST /api/receipts/read`, body `{ mediaId: string }`:
    - 401 when not signed in
    - 403 for family users
    - 404 `{ code: 'err.notFound' }` for an unknown media id
    - 415 `{ code: 'purchasing.err.notImage' }` for a non-image
    - 200 with the `OcrResult`
  - `today` comes from the server clock (`clock.ts`), the same day the actions use.
  - Web: `export async function readReceipt(mediaId: string, signal?: AbortSignal): Promise<OcrResult>` in `lib/ocr.ts`, using the same `api` helper as `uploadMedia`.

# Round 16 Phase 2 (Owner, roles, owner approvals) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Round 16 points 8–10:
- an Owner above Management (Benjamin Cass);
- an Admin › Roles grid (Hidden / View / Edit per role and menu item);
- owner approval for Management's plans and pricing, holidays and weekly budget changes.

**Architecture:**
- The menus move from `apps/web/src/app/nav.ts` into a shared rule, `rules/access.ts`. The server can then enforce the grid, and the web builds its menus from the same data.
- Actions keep their existing `can`, so today's fine-grained rights are untouched. `execute()` adds two checks:
  - **Area check.** Each staff action maps to a menu key. If the role's level there is below Edit, the action is refused. If the role was granted Edit where it had none by default, `can` is evaluated as the area's base role.
  - **Owner gate.** Plans and pricing, holiday and weekly budget actions by a role whose switch is on become a `ChangeRequest` the Owner approves. The approval replays the action as the submitter, the way gated profile changes already work.
- The Owner counts as Management everywhere (`isMgmt`, `hasRole(u,'mgmt')`, notifications to `mgmt`), so the ~150 existing checks need no edit.

**Tech Stack:** TypeScript, immer actions, React 18, vitest, Playwright; pnpm monorepo.

**Spec:** `docs/superpowers/specs/2026-10-30-round16-design.md` §Phase 2 (points 8–10), Conventions and Testing.

**Depends on:** phase 1 (`club.updateSettings` with `noticeDays`, `prices.set` with the new fees: both are pricing-gated here).

## Rulings made while writing this plan

- **R1 The home item ('today') is not in the grid.** Each role's home screen is fixed (Arrivals, Health, Menu…). The grid covers every other menu key.
- **R2 Base role per area.** When the grid grants Edit beyond the defaults, `can` is evaluated as `AREA_BASE[key]`. The UI renders that screen as the base role too.
  - `lobby`: members, enquiries, renewals, venue, surveys
  - `kitchen`: menu, lunch, feedback
  - `nurse`: hchecks, readings
  - `activity`: log, camera, calendar
  - `finance`: billing, payments, budget, receipts, spending, stock, guests, directory
  - `mgmt`: everything else (tasks, requests, contacts, reviews, report, monthReport, insights, broadcast, hr, plans)
- **R3 Link-only extras stay as they are.** `EXTRA` in nav.ts (lobby: calendar, photos, guests, surveys, celebrations…) is not part of the grid. A key the grid sets to Hidden is removed from the extras too.
- **R4 View in the UI.**
  - The two default View cells (Front desk Billing, Management Receipts) hide their buttons explicitly.
  - Any other cell the Owner later sets to View shows a "View only" banner under the screen title, and the server refuses the action with `err.viewOnly`. The error toast already shows domain errors.
  - Hiding every button on every screen is not in scope (KC to be told).
- **R5 Only the Owner can give or take the Owner role** (`staff.create` / `staff.update` with `role: 'owner'`). Management can no longer edit an Owner's staff row.
- **R6 Approval sections:**
  - New `ReviewSection` values `'pricing' | 'holiday' | 'budget'`, and a new target type `'club'`.
  - The Approvals hub gets a new type `'owner'` for them. The hub's existing `'profile'` type excludes those sections.
  - Only the Owner approves or rejects them.
- **R7 Seeded pending holiday:** Ega asks for `calendarEvent.create { kind: 'closed', title: 'Staff training day', titleId: 'Hari pelatihan staf' }` on the first open weekday on or after 2026-12-14 relative to the seed's month. It waits for Benjamin, with an owner notification.

## Review Focus

1. **The Owner sees everything Management sees:** notifications to `mgmt`, the Approvals hub's existing types, every Management screen. *Test: Task 1.*
2. **A role's access changed while they are on the screen:** the next action is refused with `err.viewOnly`, and the menu updates on the next state push. *Test: Task 3 (server refusal).*
3. **An owner-gated change that no longer fits when approved** (for example a holiday on a day that has since been rented): approval fails with the action's own error, and the request stays pending. *Test: Task 6.*
4. **Management withdrawing a pending pricing change:** `review.withdraw` works for `'club'` targets. *Test: Task 6.*
5. **Grid defaults equal today's access:** every role's menu and every action's `can` are unchanged except the two KC changes. *Test: Task 2 and Task 3.*

# Round 17 Phase 2 (Roles, few-visits alert, Settings, terms) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Round 17 points 8–11:
- Admin › Roles as a role list, then View and Edit checkboxes per menu;
- the few-visits alert (rule, notification, Next month card and list, call log, Also today);
- Admin › Settings (notice period, few-visits settings, terms);
- terms and conditions (versioned, editable, family first-login and re-agree gate, Me row).

**Architecture:**
- Roles keep the round 16 grid (`ClubSettings.access`, `permit()` in `actions/framework.ts:151-165`). Only the screen and its save action change: one `access.setRole` writes a whole role's draft.
- Few visits is a pure rule (`rules/fewVisits.ts`) read by a daily job, the Next month card and Also today; calls are a new collection `visitCalls`.
- Terms live in `ClubSettings.terms` (versions) and `FamilyContact.termsAgreed`. `execute()` refuses family actions until the current version is agreed; the family shell shows a full-screen gate.

**Tech Stack:** TypeScript, immer actions, React 18, vitest, Playwright; pnpm monorepo; Hono + Drizzle + Postgres server.

**Spec:** `docs/superpowers/specs/2026-11-03-round17-design.md` §Phase 2 (points 8–11), Conventions and Testing. KC approved the spec on 3 Nov.

## Global Constraints

- Shared immer actions in `packages/shared/src/actions`, pure rules in `rules`. Role checks server-side through `can` and `permit()`.
- Dense phone-first UI, 44 px targets, ink, grey and white with the warm staff skin, no pastel tints; iOS grouped lists on phones. Screenshots at phone, tablet and desktop.
- Every string in EN and ID.
- Seed RNG-neutral, `CP_SEED_SMALL=1` working, club state under 7,500,000 characters at the real date and at 2026-12-30.
- Minimal tests: typecheck, unit tests for new rules and actions, one e2e pass for the phase (phone).
- Roles: "Ticking Edit ticks View; unticking View unticks Edit; neither = the menu is hidden and its screen refused." "Saving a draft writes only cells that differ from the default, so untouched default-off cells stay 'never set'."
- Few visits: "Alert day for month M = `noticeDeadline(M+1) − daysBeforeDeadline` (default 2)" (15 Nov for November). "Flagged: an active member with fewer than `below` (default 5) visit days from the 1st of M up to today."
- Terms: "**Agree and continue** is disabled until the reader reaches the end … if the text fits without scrolling it is enabled at once."

## Rulings made while writing this plan

- **R1 Role page groups** come from the sidebar layout: `nav.ts` exports `menuGroups(): { label: string | null; keys: string[] }[]` built from `MGMT_LAYOUT` (`nav.ts:41-48`) without `today` and `roles`; menu keys not in that layout (`contacts`, `requests`, `settings` is in Club) go to the first group, whose label is `nav.g_general` ("General" / "Umum").
- **R2 `access.setRole`** input `{ role: GridRole; levels: Record<string, AccessLevel>; approvals: Record<OwnerKind, boolean> }`, Owner only. For each `MENU_KEYS` key: a level equal to the default is deleted; a default-off key saved as `off` is deleted (stays never-set, so `permit()` L157 keeps leaving it to `can`; this also clears round 16's explicit Hidden on such keys); anything else is stored. Approvals equal to `ownerApprovalOn`'s default are deleted. Sets `ClubSettings.accessChanged[role] = { by: user.id, at: ctx.nowDT }`; notifies `toRoles: [role]` with `access.notif.changed`. `access.set` and `access.setOwnerApproval` are removed with their UI.
- **R3 Unsaved changes:** switching role or going back to the list with a dirty draft opens a ConfirmDialog ("Discard 3 changes?"); a `beforeunload` handler covers leaving the page. No router blocker (the app's router is not a data router).
- **R4 New `Checkbox`** in `apps/web/src/components/ui` (`{ checked: boolean | 'mixed'; onChange(next: boolean): void; label: string; disabled?: boolean }`, 44 px target, ink when checked, `aria-checked="mixed"`).

- **R6 Owner gate for settings:** `ownerKindOf` (`ownerGate.ts:13`) returns `'pricing'` for `club.updateSettings` only when the input has `noticeDays` or `flexQuota`; `fewVisits` alone applies at once.
- **R7 `club.updateSettings`** also accepts `fewVisits: { below: int 1–31; daysBeforeDeadline: int 0–14 }`.
- **R8 Few visits "left out"** uses existing helpers: `membershipStatus(m, today) === 'active'` (core.ts L90), the current membership's `start <= monthStart(month)`, `!onLeaveIn(m, month)` (leave.ts L22), `nextMonthPlans(s, today)` status not `'stop'` or `'leave'` (renewals.ts L242), and `askedInApp(s, m, nextMonth)` falsy (renewals.ts L67).
